# OpenBy 开发文档

> 本文保留立项时的方案调研与技术设计；项目现已实现，当前使用与构建方式请参阅 [README](../README.md)。  
> 调研日期：2026-08-31  
> 产品定位：按“文件类型 + 所在文件夹”把文件快速转交给指定 macOS 应用

## 1. 结论先行

OpenBy 不应尝试修改 macOS 不存在的“文件夹级默认应用”设置。正确实现方式是让 OpenBy 成为相关文件类型的系统默认处理器，再由 OpenBy 根据文件 URL 的路径匹配规则，显式调用目标应用打开文件。

推荐技术方案：

- 语言：Swift。
- UI：AppKit 为主；设置窗口可少量使用 SwiftUI，但不在文件打开热路径初始化。
- 系统接口：`NSApplicationDelegate`、`NSWorkspace`、`UniformTypeIdentifiers`。
- 形态：一个原生 `.app`，一个进程，不安装常驻 Helper，不使用 Electron、Tauri、WebView 或脚本运行时。
- 数据：小型 Codable 配置文件，原子写入；运行时加载为不可变规则快照。
- 路由策略：规则从上到下匹配，第一条命中即停止；没有命中时使用该文件类型的默认回退应用。
- 发布：首版采用非沙盒、Hardened Runtime 的直接分发版本；若以后上架 Mac App Store，再单独评估 Helper 和沙盒权限。

这个设计与 OpenIn 对外公开的核心工作流一致，但实现范围更窄：OpenBy 首版只做好文件路由，不加入浏览器、邮件、JavaScript、正则重写和历史数据库，因此可以更快、更稳定、更小。

## 2. 产品目标

首版必须可靠完成以下场景：

1. 用户添加文件类型，例如 `pdf`。
2. OpenBy 记录接管前的默认应用，例如“预览”，作为回退应用。
3. 用户添加规则：`~/Documents/文献/` 内的 PDF 使用 PDF Expert。
4. OpenBy 成为 PDF 的系统默认处理器。
5. 用户双击 PDF 时：
   - 位于“文献”文件夹或其子文件夹：使用 PDF Expert；
   - 位于其他文件夹：使用“预览”。
6. 支持一次打开多个文件；不同文件可被分组转发到不同目标应用。
7. 禁用或删除某个文件类型时，可以恢复接管前记录的默认应用。

首版明确不做：

- URL、浏览器、邮件和电话链接路由。
- JavaScript、Shell、自定义脚本或插件。
- 正则表达式路径规则。
- 云同步、账户、遥测、自动更新框架。
- “根据来源应用”“根据快捷键”“根据专注模式”等高级条件。
- 文件内容识别；首版只依据系统 UTI、扩展名和路径。

这些约束是保证体积、速度和稳定性的关键，不是永久限制。

## 3. GitHub 与公开项目调研

### 3.1 OpenIn 4：产品行为参考，非源码参考

项目主页：[OpenIn 4](https://loshadki.app/openin4/)

OpenIn 是闭源商业软件，无法检查其内部源码。能够从官方文档确认的事实包括：

- 它先成为某个文件类型的默认处理器，再把文件路由给目标应用。
- 每个处理器维护候选应用和有顺序的规则。
- 特定规则在前、默认规则在后；匹配后只剩一个目标时直接打开。
- 文件规则支持路径例外。
- App Store 版本受沙盒限制，部分高级功能需要额外 Helper；官网和 Setapp 版本不受沙盒限制。
- 它还包含 JavaScript、Shell、URL 重写和历史等高级功能。

OpenBy 借鉴其“处理器 → 有序规则 → 默认回退”的产品模型，但不照搬高级功能。由于没有源码，本文关于 OpenIn 内部模块划分的描述均只作为推断，不作为实现依据。

### 3.2 jmarette/openwith：默认关联层的主要源码参考

仓库：[jmarette/openwith](https://github.com/jmarette/openwith)  
许可证：MIT / Apache-2.0  
定位：用 Swift 管理文件类型、UTI 和 URL Scheme 的默认应用。

值得参考的设计：

- 优先使用现代 `NSWorkspace` API；仅在需要区分 Viewer/Editor 角色时退回 Launch Services C API。
- 核心逻辑与 CLI、GUI 分离，前端只是薄壳。
- 修改默认关联后重新读取系统状态验证，不能只相信 API 调用成功。
- 测试中注入假的 Launch Services Provider，避免单元测试污染开发机的真实默认关联。
- 应用用 Bundle Identifier 作为稳定身份，用 `.app` 路径作为解析结果或后备信息。

需要注意：该项目只管理全局默认关联，不做按文件夹路由。OpenBy 只参考其关联管理、验证和可测试性设计。

### 3.3 DevShedLabs/mac-sethandler：最小可行关联证明

仓库：[DevShedLabs/mac-sethandler](https://github.com/DevShedLabs/mac-sethandler)  
许可证：MIT  
定位：约 50 行 Swift 的默认文件应用设置工具。

其核心流程是：

1. 使用 `UTType(filenameExtension:)` 把扩展名解析为 UTI。
2. 使用 `LSSetDefaultRoleHandlerForContentType` 把某个 Bundle ID 设为处理器。

它证明默认关联本身不需要大型框架。不过 OpenBy 不应直接以旧 C API 为主，因为 Apple 已提供现代 `NSWorkspace.setDefaultApplication` 方法。C API只作为兼容性后备并隔离在 Provider 中。

### 3.4 philocalyst/infat：原生、单二进制和声明式配置参考

仓库：[philocalyst/infat](https://github.com/philocalyst/infat)  
定位：通过 Swift Package Manager 构建的原生 CLI，管理扩展名、UTI 和 Scheme 关联。

值得参考的部分：

- 使用 `NSWorkspace`、Launch Services 和 `UTType`，不依赖跨平台运行时。
- 单二进制和小型声明式配置适合快速启动。
- 清楚区分扩展名、UTI 和类型继承，避免把 `.yml` 与 `.yaml` 误当成完全独立的系统类型。

OpenBy 的用户界面不采用 TOML，但配置文件同样要带 `schemaVersion`，便于以后迁移。

### 3.5 0xdps/default-tamer：有序路由模型参考

仓库：[0xdps/default-tamer](https://github.com/0xdps/default-tamer)  
许可证：MIT  
定位：把自身设为默认浏览器，再根据来源应用和 URL 规则把链接路由到不同浏览器。

它处理的是 URL 而不是文件，但工作模式高度相似：

- 规则按顺序计算；第一条命中规则生效。
- 未命中时使用明确的 fallback。
- 本地处理，不需要网络请求。

OpenBy 应采用同样简单且可解释的“first match wins”模型，不在首版引入复杂规则树或通用表达式引擎。

### 3.6 SwiftDefaultApps：只作历史参考

仓库：[Lord-Kamina/SwiftDefaultApps](https://github.com/Lord-Kamina/SwiftDefaultApps)

它展示了 Launch Services 的 UTI、Viewer/Editor 角色和候选应用模型，但项目长期依赖已废弃接口。OpenBy 不复用其旧 Preference Pane 架构，也不以废弃 API 为基础。

### 3.7 Tauri/tao 的 macOS 26 问题：反向技术选型依据

问题记录：[tauri-apps/tao #1206](https://github.com/tauri-apps/tao/issues/1206)

该问题报告称，在 macOS 26.4.1 上，已经运行的 Tauri/tao 应用可能收不到带 quarantine 属性文件的 `application:openURLs:` 回调。无论最终属于系统还是框架问题，它都说明在 OpenBy 这种以文件打开事件为核心的应用里，多一层跨平台事件桥接会增加风险。

因此 OpenBy 直接使用 AppKit，不采用 Tauri 或 Electron。也绝不能为了规避问题而删除用户文件的 `com.apple.quarantine` 属性。

## 4. macOS 实现机制

### 4.1 声明自己可以处理文件

应用在 `Info.plist` 的 `CFBundleDocumentTypes` 中声明支持的内容类型。为了允许用户以后添加不同文件类型，OpenBy 可声明通用的 `public.item`：

- `CFBundleTypeRole = Viewer`
- `LSHandlerRank = Alternate` 或 `None`
- `LSItemContentTypes = [public.item]`
- `LSSupportsOpeningDocumentsInPlace = YES`

这样 OpenBy 可以出现在 Finder 的“打开方式”候选中，但不会在未获用户选择时主动抢占所有文件。

参考：[Apple CFBundleDocumentTypes](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundledocumenttypes)

### 4.2 设置默认处理器

首选现代 API：

```swift
NSWorkspace.shared.setDefaultApplication(
    at: openByApplicationURL,
    toOpen: contentType
) { error in
    // 完成后必须重新读取系统默认值验证
}
```

在接管之前，先通过 `NSWorkspace.urlForApplication(toOpen:)` 读取原默认应用并保存。如果当前默认已经是 OpenBy，则不能覆盖此前保存的回退应用。

macOS 26.4 起可能针对每次默认应用变更显示系统确认框。OpenBy 的 UI 必须把它视为正常流程：一次只申请一个文件类型，完成后重新读取状态，用户拒绝时保留配置但显示“尚未接管”。

参考：[Apple NSWorkspace](https://developer.apple.com/documentation/appkit/nsworkspace)

### 4.3 接收 Finder 打开的文件

系统把文件 URL 交给：

```swift
func application(_ application: NSApplication, open urls: [URL])
```

OpenBy 不使用 `NSDocument`，也不读取或修改文件内容。收到 URL 后立即交给路由核心；设置窗口、图标扫描和更新检查都不能阻塞这条路径。

参考：[Apple NSApplicationDelegate application(_:open:)](https://developer.apple.com/documentation/appkit/nsapplicationdelegate/application(_:open:))

### 4.4 显式转交目标应用

必须显式指定目标 `.app` 的 URL：

```swift
NSWorkspace.shared.open(
    fileURLs,
    withApplicationAt: targetApplicationURL,
    configuration: .init()
) { _, error in
    // 记录成功或进行可控降级
}
```

不能调用不指定应用的 `NSWorkspace.open(fileURL)`，因为系统默认处理器正是 OpenBy，这会产生递归打开。

参考：[Apple NSWorkspace.open(_:withApplicationAt:configuration:)](https://developer.apple.com/documentation/appkit/nsworkspace/open(_:withapplicationat:configuration:completionhandler:))

## 5. 总体架构

```text
Finder / Spotlight / 其他应用
             │ 打开一个或多个文件 URL
             ▼
       OpenBy AppDelegate
             │
             ▼
      OpenRequestCoordinator
             │ 标准化 URL、批量请求去重
             ▼
        RuleEngine（纯 Swift）
             │ 第一条命中规则 / fallback
             ▼
     [目标 App : 文件 URL 列表]
             │ 按目标应用分组
             ▼
    WorkspaceOpening（NSWorkspace）
             │
             ├── PDF Expert
             └── Preview
```

模块职责：

- `AppDelegate`：只接收生命周期和文件打开事件。
- `OpenRequestCoordinator`：处理冷启动/热启动时序、批量文件、去重和错误汇总。
- `RuleEngine`：纯函数式匹配，不接触 UI、磁盘和 `NSWorkspace`。
- `AssociationProvider`：查询、设置、验证和恢复系统默认应用。
- `ApplicationResolver`：根据 Bundle ID 找到已安装应用，过滤 OpenBy 自己。
- `WorkspaceOpening`：把文件显式转发给目标应用。
- `ConfigurationStore`：原子保存、迁移、校验并发布不可变配置快照。
- `SettingsUI`：管理文件类型、规则顺序、文件夹和应用选择。

所有系统边界都用协议隔离，单元测试使用 fake 实现。

## 6. 配置模型

建议的数据结构：

```swift
struct Configuration: Codable {
    let schemaVersion: Int
    var handlers: [FileHandler]
}

struct FileHandler: Codable, Identifiable {
    let id: UUID
    var contentTypeIdentifier: String
    var displayExtensions: [String]
    var enabled: Bool
    var fallbackApplication: ApplicationReference
    var previousDefaultApplication: ApplicationReference?
    var rules: [FolderRule]
}

struct FolderRule: Codable, Identifiable {
    let id: UUID
    var enabled: Bool
    var folderPath: String
    var includesDescendants: Bool
    var targetApplication: ApplicationReference
}

struct ApplicationReference: Codable, Equatable {
    var bundleIdentifier: String
    var lastKnownPath: String?
    var displayName: String
}
```

关键约束：

- Bundle ID 是应用身份；安装路径只是缓存，因为应用可能移动或升级。
- 文件类型的系统身份是 UTI；扩展名用于用户展示和初始解析。
- 规则顺序必须持久化。
- 删除处理器前尝试恢复 `previousDefaultApplication`，但仅当当前默认仍是 OpenBy 时恢复，避免覆盖用户之后手动做出的选择。
- 每次写入使用 `.atomic`，保留最近一份可读备份；加载失败时不覆盖损坏文件。

## 7. 路由算法

首版算法保持线性且无 I/O：

```text
输入：fileURL、已加载的不可变 Configuration

1. 验证 URL 是本地 file URL。
2. 标准化路径，移除 . 和 ..；不解析符号链接，不读取文件内容。
3. 根据 UTI/扩展名找到启用的 FileHandler。
4. 从上到下遍历启用的 FolderRule：
   a. 进行有路径边界的“位于文件夹内”比较；
   b. 命中后返回 targetApplication。
5. 未命中返回 fallbackApplication。
6. 解析 Bundle ID 为应用 URL。
7. 若目标缺失，尝试 fallback；fallback 也缺失则报告错误，绝不调用系统默认打开。
8. 多文件请求按目标应用分组，每个目标只调用一次 NSWorkspace.open。
```

路径匹配不能简单使用无边界的字符串 `hasPrefix`。例如规则目录 `/A/Paper` 不应匹配 `/A/Papers2/file.pdf`。实现时应比较标准化后的路径组件，或确保前缀后紧跟路径分隔符。

首版不自动 `resolvingSymlinksInPath()`：它会访问文件系统，网络盘上可能阻塞，并会改变用户对“所在文件夹”的直觉。符号链接行为需要在测试后明确写入帮助文档。

## 8. 设置界面流程

设置窗口采用单窗口主从布局，不再按技术概念拆成多个页签：左侧选择管理的文件类型，右侧一次完成启用状态、位置规则、其他位置的打开应用。

### 8.1 首次使用与文件类型列表

- 空配置时显示三步式引导，主操作为“添加文件类型”；可选择图片、视频、音频、文档预设，手动输入一个或多个后缀，或添加示例文件。预设只填充草稿，确认前可修改名称、删除后缀或加入新后缀；整个内容区也接受文件拖入。
- OpenBy 从示例文件识别扩展名和 UTI，左侧只展示“.PDF 文件”等用户可理解的信息。
- UTI、Bundle ID 和配置路径不进入主任务流。
- 添加后先配置位置规则，最后点击“启用自动打开”并处理系统确认。

### 8.2 当前文件类型的完整设置

- 顶部以颜色和文字展示“已启用 / 尚未启用 / 需要检查”，不用“接管”等内部术语。
- 规则使用“文件夹及其子文件夹 → 应用”的自然语言展示，并支持拖动排序。
- 编辑规则时通过系统面板选择文件夹和应用，实时预览完整规则语义，不要求用户输入绝对路径。
- 未命中规则时使用的应用单独放在“其他位置”区域，不再作为一条假的回退规则混在表格内。
- 移除正在启用的文件类型前，必须先成功恢复原默认应用；恢复失败则保留配置，避免留下无法路由的系统默认关联。

### 8.3 格式组

- 一个组在左侧占一项，共用一套有序位置规则和“其他位置”应用。通过「更多 → 编辑格式组」修改组名与后缀列表。
- 新格式组按显式后缀精确匹配，不自动扩展到图片或视频的所有子类型；旧单类型配置继续使用原匹配语义。
- 同一后缀或同一系统文件类型不能同时属于两个组，避免打开规则冲突。`jpg/jpeg` 等系统别名可能共用默认应用关联。
- 按系统文件类型去重后，逐一启用、验证和恢复。组内各类型分别保存原应用；部分成功显示真实进度，可重试剩余类型或整体停用。
- 编辑时先恢复被移除类型的原应用，成功后才保存新成员；添加类型保留已有规则，并提示启用新增格式。
- 配置版本升级为 2；版本 1 自动迁移，保留原规则和默认应用记录。

## 9. 性能和体积指标

开发过程中设置可测量门槛：

| 指标 | 目标 |
|---|---:|
| 热进程收到 URL 到发出 `NSWorkspace.open` | P95 < 10 ms |
| 冷启动收到 URL 到发出转交请求 | P95 < 150 ms（Apple Silicon SSD） |
| 1,000 条规则单文件匹配 | < 1 ms |
| 空闲常驻内存 | < 30 MB |
| Release 通用版 `.app` | < 15 MB |
| 正常路由磁盘写入 | 0 次 |
| 正常路由网络请求 | 0 次 |

实现原则：

- 不引入第三方依赖。
- 文件热路径不初始化设置 UI，不扫描 `/Applications`，不解析图标，不写日志。
- 配置保存时预编译/标准化规则，路由时只读取快照。
- 小规模规则使用线性扫描；真实数据通常少于几十条，线性结构比树或通用规则引擎更简单、缓存友好。
- 批量文件按目标应用合并调用。
- 文件事件立即交给后台路由队列，不设置转发前等待；不同目标应用独立定位和转发，同一目标保持顺序。
- 单进程后台常驻，关闭设置窗口不会退出；菜单栏提供设置、登录启动和主动退出。无轮询保活。
- 路由配置为不可变快照，类型匹配缓存上限 256，应用地址缓存上限 128；缓存有效期 5 分钟，并在配置变更、应用启动/退出、系统唤醒或转发失败时失效（类型缓存随配置重建或有效期到期重新匹配）。
- 每个目标的请求有 30 秒超时，超时释放调度状态，不自动重发；迟到回调按请求 ID 忽略。
- 最近 100 组分段计时和 20 条错误仅保留在内存，诊断页按需异步读取。系统回调完成不等于文档窗口可见。
- Release 开启优化并剥离调试符号；不内置更新框架和 Web 资源。

## 10. 稳定性与安全设计

### 10.1 防递归

- 配置时禁止把 OpenBy 选为目标或 fallback。
- 转发前再次比较目标 Bundle ID 与 OpenBy Bundle ID。
- 每次调用都显式指定目标应用，绝不依赖系统默认应用。

### 10.2 应用被移动、升级或卸载

- 每次路由优先通过 Bundle ID 调用 `NSWorkspace.urlForApplication(withBundleIdentifier:)`。
- `lastKnownPath` 只作为显示和后备信息。
- 目标不存在时尝试 fallback，并给出一次非阻塞通知。
- 不在路由热路径做全盘应用扫描。

### 10.3 默认关联被其他应用抢回

- 启动设置窗口时检查；不需要常驻轮询。
- 状态不一致时明确提示用户重新接管。
- 不在后台悄悄反复改回，尊重用户和系统确认。

### 10.4 配置损坏

- 配置有 `schemaVersion` 和严格校验。
- 写入采用临时文件 + 原子替换。
- 保留一份上次成功配置；主配置损坏时只读备份并提醒，不自动覆盖原始证据。
- RuleEngine 永远能构造安全的空配置；不能因单条坏规则导致应用崩溃。

### 10.5 隐私

- 无网络请求、无遥测、无账户。
- 默认不保存打开历史和文件路径日志。
- 错误日志对路径做用户目录缩写或脱敏。
- 不读取文件内容，不修改文件扩展属性，不删除 quarantine。

## 11. 沙盒与分发策略

首版建议直接分发、不开启 App Sandbox，理由如下：

- OpenIn 官方说明其 App Store 版本部分高级功能需要 Helper，而非沙盒版本不需要。
- OpenBy 是用户主动安装的系统文件路由器；增加 Helper 会扩大代码量、安装复杂度和故障面。
- 单一非沙盒应用仍应开启 Hardened Runtime，并在正式发布时 Developer ID 签名和 notarization。

这不代表需要管理员权限。设置当前用户的默认应用和显式打开文件正常情况下不应要求 root。

如果未来要上架 Mac App Store，应单独建立发行目标，重新验证：

- Finder 传入文件 URL 的沙盒访问。
- 设置默认应用 API 的限制与系统确认。
- 是否确实需要 Helper，以及 Helper 的通信、签名和更新一致性。

## 12. 测试计划

### 12.1 RuleEngine 单元测试

- 规则优先级和 first-match-wins。
- 默认 fallback。
- 文件夹本身、直接子文件和多级子文件。
- 相似目录名边界：`Paper` 与 `Papers2`。
- 中文、空格、emoji、组合 Unicode 字符。
- `.`、`..`、尾部斜杠。
- 是否包含子文件夹开关。
- 大小写敏感卷与默认 APFS 行为。
- 符号链接行为。
- 1,000/10,000 条规则基准测试。

### 12.2 系统集成测试

- 冷启动单文件、热启动单文件。
- 一次打开多个文件，且命中不同目标应用。
- Finder、Spotlight、终端 `open` 和其他应用发起的打开。
- 目标应用未运行、已运行、被移动、被卸载。
- 目标应用打开失败时的 fallback 和错误提示。
- 接管、用户拒绝系统确认、验证、恢复原默认应用。
- 另一个应用抢回默认关联后的状态展示。
- iCloud Drive、外接盘、网络盘和只读文件。
- 带 quarantine 的下载文件；不得修改其扩展属性。

### 12.3 系统版本矩阵

建议最低支持 macOS 14，测试：

- macOS 14 Sonoma（最低版本）。
- macOS 15 Sequoia。
- macOS 26 当前稳定版。
- Apple Silicon 为主；正式通用版发布前补 Intel 验证。

如果实际目标用户都已升级到 macOS 15/26，可以把最低版本提高到 15，以缩小测试矩阵。该决定应在编码前根据用户机器版本确认。

## 14. 开发阶段

### 阶段 0：最小技术验证

- 建立空白 AppKit 应用。
- 声明 `public.item`，验证 Finder 能把 PDF URL 交给 `application(_:open:)`。
- 显式用 `NSWorkspace` 转发给“预览”和 PDF Expert。
- 验证冷启动、热启动、多文件和 macOS 26 quarantine 场景。

退出标准：连续 100 次打开没有漏事件、递归或前台闪窗。

### 阶段 1：无 UI 路由核心

- 完成数据模型、PathMatcher、RuleEngine、配置存储。
- 完成应用解析、分组转发和错误降级。
- 单元测试和基准测试达到本文件指标。

### 阶段 2：默认关联与设置 UI

- 添加/删除文件类型、文件夹规则和应用选择。
- 接管前记录原默认应用；设置后读取验证；停止接管时安全恢复。
- 提供规则测试和诊断页面。

### 阶段 3：兼容性与发布

- 完成 macOS 14/15/26 测试矩阵。
- Release 性能、内存和体积测量。
- Hardened Runtime、Developer ID、notarization 和 DMG。
- 编写用户安装、卸载及恢复默认关联说明。

## 15. 编码前仍需确认的两项产品决定

1. **最低 macOS 版本**：建议 macOS 14；需要根据实际机器版本最终确定。
2. **进程生命周期（1.1）**：单进程后台常驻，转发结束和关闭设置窗口均不退出。菜单栏可打开设置、管理登录启动或主动退出；登录启动不弹设置。

除此之外，技术路径已经可以直接进入阶段 0，无需继续扩大调研范围。
